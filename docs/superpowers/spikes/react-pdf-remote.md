# Spike 2 — react-pdf inside a Vite remote app (SF-1 / FI-234)

**Verdict: GO** — react-pdf (pdf.js) works in a Vite remote-app context with the worker
loaded via Vite `?url` import. All checklist items PASS.

- Sandbox: `/tmp/sf1-spikes/spike2/` (single Vite + React 18 + TS app simulating the remote;
  federation wiring itself was proven in Spike 1, not repeated here).
- Environment: Node v24.10.0, no browser available — evidence is server-level (curl) +
  pixel-level rendering in Node via `@napi-rs/canvas` using the *same* pdfjs-dist copy
  react-pdf depends on.

## Working config

`vite.config.ts`:

```ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  optimizeDeps: {
    // Pre-bundle pdfjs-dist main entry so dev resolves like prod build.
    include: ['pdfjs-dist'],
    // Worker imported via ?url — exclude so Vite serves/emits the raw asset
    // instead of wrapping it in the dep optimizer.
    exclude: ['pdfjs-dist/build/pdf.worker.min.mjs'],
  },
})
```

Worker wiring (the load-bearing lines):

```ts
import { Document, Page, pdfjs } from 'react-pdf'
// Worker via Vite ?url import — the pattern under test.
import workerUrl from 'pdfjs-dist/build/pdf.worker.min.mjs?url'

pdfjs.GlobalWorkerOptions.workerSrc = workerUrl
```

A `src/vite-env.d.ts` with `/// <reference types="vite/client" />` provides the
`?url` module type declaration for TS.

## Caveats / notes for SF-10

1. **Federation + worker URL**: `?url` yields a root-relative URL (`/assets/...`).
   Under Module Federation the remote is served from a different origin than the
   host, so `workerSrc` becomes cross-origin. `new Worker(crossOriginUrl)` is
   blocked unless the worker response carries proper CORS headers
   (`Access-Control-Allow-Origin`) — same-origin worker scripts are not subject to
   CORS, cross-origin ones are. Options if it bites: serve remotes under the same
   origin via host proxy/rewrite, or fetch the worker bytes and create a blob URL.
   (Spike 1 proved federation wiring; this CSP/CORS worker case is the main
   residual risk to validate in integration.)
2. **CSP**: a site CSP with `worker-src 'self'` covers same-origin `?url` workers;
   `blob:` workers would need `worker-src 'self' blob:`. Also pdf.js may fetch
   `cMapUrl`/`standardFontDataUrl` for CJK/standard fonts — either copy those dirs
   into `public/` or set them to `undefined` for Latin-only documents (spike did
   the latter; worked for Helvetica).
3. **Bundle size**: pdf.js adds ~600 kB minified (~185 kB gzip) to the remote main
   chunk. SF-10 should lazy-load the viewer (`import()` of the Document page) and/or
   split pdfjs into its own chunk (`manualChunks`). The worker asset itself (~1 MB,
   ~300 kB gzip over the wire) is only fetched when a PDF is opened.
4. **Version pinning**: react-pdf 10.5.0 pins pdfjs-dist 5.4.296 internally. Do NOT
   add pdfjs-dist as a direct dependency with a different version — the worker and
   API versions must match exactly or pdf.js throws. If you need the raw pdfjs API
   alongside react-pdf, import `pdfjs` from `react-pdf` itself.
5. The `optimizeDeps` include/exclude combo in the snippet is the one verified
   working; removing the exclude is not recommended (Vite would try to pre-bundle
   the worker into the dep graph instead of treating it as a raw asset).
